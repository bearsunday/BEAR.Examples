# 評論のセルフレビュー

`docs/framework-critique.md` を読み返し、以下のパターンに該当する箇所を点検する。

- **(A) ナンセンス系** — 「OOP の弱点は OOP を学ぶコストが必要」のように、特徴を
  そのままネガティブに言い換えただけのもの
- **(B) 時代遅れの前提** — StackOverflow 回答数、ドキュメント発見性、IDE 可視性、
  人材採用、人間が学ぶ認知負荷など、2026 年の AI エージェント中心ワークフローでは
  重みが下がっている軸
- **(C) 単純な二項対立** — 同じ対立構造の使い回し、ニュアンスを失わせる対句
- **(D) 軸の不整合** — 自分が `skill-proposals.md` で提案した未来像と矛盾する
  論拠を立てている

結論: **評論の半分以上が「人間が全部書く時代」の前提に立っている。**
私自身がスキル提案で「AI エージェントが回す」未来を描いておきながら、評論では
旧パラダイムで弱点を数えていた。整合していない。

---

## A. ナンセンス系の批判

### A1. §8.1「BEAR.Sunday は最初から ResourceObject を理解しないといけない」

> Laravel は「ルートに closure」から始められるが、BEAR.Sunday は最初から
> ResourceObject を理解しないといけない。

**これは「OOP の弱点は OOP を学ぶ必要があること」と同じ構造。** ResourceObject を
1級市民にしたフレームワークなのだから「最初から ResourceObject」は特徴であって
弱点ではない。「弱点」フレームに無理やり押し込んだだけ。

しかも 2026 年の前提では: ResourceObject の最初の1個は AI が scaffold する
(`bear-skills:scaffold-resource` で 30 秒)。**ユーザーが「理解する」前にコードが
動く** 時代に「理解しないといけない」は的外れ。

### A2. §8.2「商業案件で『BEAR.Sunday できる人』を探すのは難しい」

> PHP 圏では小さい。商業案件で「BEAR.Sunday できる人」を探すのは難しい。

これは StackOverflow 回答数論法と同じ構造。「人手の数」を競争力の根拠に置いている。

2026 年の現実: Claude Code / Codex / Cursor が BEAR.Sunday のコードベースを
読んで書ける。**「できる人」の供給はモデルの読解力に置き換わっている。** ニッチな
技術スタックほど AI と人間の埋まる役割比率が変わる。むしろ「BEAR.Sunday が
できる AI エージェント」を作れるかが論点で、それは framework-critique.md ではなく
skill-proposals.md の話題。

### A3. §11「Laravel は妥協で広がり、BEAR.Sunday は妥協しないことで深まった」

美しい対句だが、両方を貧しく描いている。Laravel は「人間 DX に妥協しない」
方向で深いし、BEAR.Sunday は「セマンティクスに妥協しない」方向で深い。
**両方とも別の軸で妥協していない**。アフォリズムの心地よさに引っ張られた。

---

## B. 時代遅れの前提

### B1. §3「ドキュメントが分散する (各 README は深いが横断ガイドが薄い)」

「分散」「横断ガイド薄い」は人間が手で読む前提の批評。Claude が `git ls-files
vendor/ray/ vendor/bear/` を grep するのに 1 秒。各 README を同時に読み込んで
synthesize するのは AI の得意分野。

**人間にとっての発見性が低い** ≠ **エコシステムの問題**。前者を後者として書いた
のが間違い。

### B2. §4「IDE で『このメソッド呼ぶと裏で何が起きるか』が見えにくい」「Stack trace が proxy で汚れる」「Ray.Di の binding error は追いにくい」

3 つとも「IDE / 人間がデバッグする」前提。

- Proxy 越しの挙動: AI が `var/tmp/*/di/` を読んで完全に追跡可能
- Stack trace の proxy ノイズ: 人間が読むときの問題、AI は気にしない
- Binding error: `bear-skills:diagnose-binding-error` (自分で提案している) で
  解消対象

**自分のスキル提案リストで解決済みと言っているものを、評論では弱点として
カウントしている**。整合性 D 違反。

### B3. §5.2「typo すると silent miss」「新規参入者は『なぜそのモジュールが選ばれたか』を追跡しにくい」

- typo の silent miss: AI 補完 + lint で消える。人間が typo するという仮定が
  古い。
- 「新規参入者は追跡しにくい」: `bear-skills:di-dump` の出番。これも自分で
  提案済み。

### B4. §6「きつかった所」のほぼ全項目

> - 初手で「context は何種類書くべき?」「Module は何個に分けるべき?」の判断が手探り

`bear-skills:add-context` で消える。

> - `#[DbQuery]` の戻り型による dispatch ルールがソースを読まないと不明

「ソースを読まないと不明」の 1 行は、AI にとっては不明ではない。むしろ
docblock に書いていない方が wishes-to-author.md の R1 の通り改善要望。

> - DI binding error のメッセージが「何が足りないか」を直接言わない

B2 と同じ。

> - `var/tmp/*/di/` のキャッシュ消し忘れで binding が反映されない事故が起きやすい

「事故が起きやすい」は人間が忘れる前提。Module 変更を検出して自動 invalidate
する skill を提案済み。

> - Pagerfanta + PDO に依存しているため `#[Pager]` の Fake が作りにくい

これだけは技術的に真の観察 (PDO 依存は AI でも変えられない)。残せる。

→ **6 項目中 5 項目が「人間がやる前提」由来**。

### B5. §8.3「クックブックが薄い」

§3 と同じ。発見性は AI 時代には別の問題。むしろ `BDR_PATTERN-ja.md` のような
密度の濃いドキュメントが既にある事実の方が重要で、「動線が弱い」は人間 UX の
問題。

### B6. §8.4「3 年後にこのプロジェクトを再現するのは多分しんどい」

「再現」を誰がやる前提? 2029 年に Claude が `git log` を読んで `composer.lock`
から依存を再構築するのは普通の作業。**「人間が肩を叩く」を仕事の前提にしている。**

## C. 単純な二項対立

### C1. §7「『正しさ』を『快適さ』より優先するフレームワーク」+「Laravel: 5 分で...BEAR: 5 分は二番目」

これが評論の中核に置かれているが、二項対立として弱い。

(a) 「正しさ vs 快適さ」自体が偽の対立。Laravel は「人間が書く快適さ」に正しさを
持っており、BEAR は「セマンティクスの正しさ」に快適さを持っている。両者の「正しさ」
の対象が違う。

(b) 「5 分で動く」は AI 時代の前提では Laravel の専売特許ではない。
`bear-skills:semantic-cycle` を回せば BEAR でも 5 分でドメイン記述から動く
HAL+JSON API が立ち上がる (skill-proposals で提案している通り)。**AI 介在で
時間軸の対立が解消** されている。

(c) 「最速で MVP 出してピボット」フェーズだと BEAR が窮屈、というのは 2020 年なら
正しい。2026 年は: AI が BEAR の構造を生成するコストが Laravel の構造を生成する
コストとほぼ等しい。ピボットコストは「型情報があるぶん安全に変えられる」BEAR の
方が低い場合すらある。

### C2. §10「採用しない方が良いケース: 短期 MVP / プロトタイプ」

C1 の帰結として直接間違っている。AI scaffolding 前提ならむしろ BEAR + skill 群が
有利。

### C3. §10「採用しない方が良いケース: チームに PHP 経験者しかおらず学習コスト予算がない」

A1 と同型のナンセンス。「学習コスト予算」を意思決定軸にしている時点で、
人間がコードを書く前提に固定されている。**AI エージェントは framework 横断で
動く** ので、チームの「PHP 経験者」しかいないという属性は採用判断の主要因に
ならない。

### C4. §10「ユーザー UI が中心 (Laravel + Inertia や Symfony + Twig の方が DX 良い)」

これは部分的に正しい (BEAR は API 中心)。ただし「DX 良い」の中身が「人間が Twig
書く快適さ」だとするとまた人間時代の話になる。Inertia / Twig / Next.js + BEAR
API みたいな組み合わせは普通に成立し、「BEAR は UI 中心に向かない」とまで
言うのは強すぎる。

## D. 軸の不整合 — 自分のスキル提案と矛盾している

`docs/skill-proposals.md` で私は次のスキルを提案している:

| スキル | 解決対象 |
|--------|---------|
| `scaffold-resource` | §8.1「ResourceObject を理解しないといけない」 |
| `scaffold-bdr` | §6「初手で何個に分けるか手探り」 |
| `scaffold-fake-sqlquery` | §6「`#[DbQuery]` dispatch ルール」 |
| `add-context` | §6「context は何種類?」 |
| `di-dump` | §5.2「なぜそのモジュールが選ばれたか追跡しにくい」 |
| `diagnose-binding-error` | §6「DI binding error 追いにくい」 |
| `semantic-cycle` | §10「短期 MVP に向かない」 |
| `check-fetch-order` | §5 で言及した列順問題 |

**つまり自分のスキル提案リストで解消対象としているものを、評論で弱点として
カウントしている**。これは批評の軸が揃っていないことの証拠。AI エージェント +
skill の世界観で書くなら、これらは「現在の弱点」ではなく「skill で埋まる隙間」
として描かれるべき。

評論を AI 介在前提で書き直すと:

- §8.1 「採用障壁が高い」 → 「人間が学ぶ前に動かせる」(skill 経由)
- §8.2 「人材プールが小さい」 → そもそも人材プールは判断軸ではない
- §8.3 「ドキュメント横断弱い」 → AI が横断する
- §6 きつかった所 → ほぼ全部 skill で消える

残る本物の弱点:
- §5.3 PDO 依存 (技術的事実)
- §5.4 Read/Write dispatch (技術的事実、wishes-to-author に R1 で対処要望済み)
- §6 Pagerfanta + Pager の Fake 困難 (技術的事実)
- §8.4 LTS 戦略 → 部分修正必要 (再現は AI が手伝うが、依存解決は人間時代と同じ)

→ 残ったのは **真の技術的制約 4 つだけ**。残り (8 項目以上) は人間時代の
バイアス由来だった。

## E. 残せる/良かった部分

公平を期すために、レビューに耐える部分も書いておく:

- §2「ALPS は意味の正規化された source of truth」「LLM 時代に特に光る」 —
  これは正しいフレーム。AI エージェントが ALPS profile を読み書きできること、
  semantic-ex が「人間の思い込みを介在させない」ことの意義は本質。
- §5.3「PDO への深い依存」 — 純粋な技術的観察、AI で解消されない
- §5.4「Read/Write dispatch が同じ穴」 — 純粋な技術的観察
- §9「強みの再確認」 — fact-based、二項対立を含まない
- §11 後半「LLM ネイティブな PHP 開発の reference として独自の地位」 — frame は
  正しい。ただし結論として置くだけでなく、評論全体をこの軸で書くべきだった。

## F. 何が起きていたか — メタな観察

評論を書く時、私は無意識に **「2018-2022 年の "framework critique" のお手本」**
を引っ張ってきていた。Hacker News や個人ブログでよく見るパターン:

1. 設計の特徴をリストアップ
2. 強み / 弱み / トレードオフをセクション分け
3. 「採用すべきケース / 採用しない方が良いケース」で締める
4. アフォリズム的な対句で結論

このテンプレート自体が **「人間が読んで人間が判断する」** ための形式。AI 時代に
そぐわない。

**正しい問いは:** 「BEAR.Sunday は AI エージェントとどう協働するときに、他の
フレームワークより優位 / 劣位か」だった。

優位面の再フレーム:
- 型情報が濃い (readonly class、attribute、interface) → AI のコード生成が
  安定する
- ALPS という形式知が一次情報 → AI に対して「この API はこう振る舞うべき」を
  曖昧さなく渡せる
- DI / context のメタ情報がコードに表現されている → AI が文脈を再構築しやすい

劣位面 (本当の弱点):
- DbQueryInterceptor の dispatch が docblock に書かれていない → AI も latent な
  挙動として推測する必要がある (改善余地)
- PDO 結合 → 別データソースへの応用に AI でも壁
- LTS バージョニング → human-time でも machine-time でも同じ複雑さ

この方向で書き直すと、評論の重心が完全にシフトする。

## G. 修正方針

framework-critique.md は **書き直すべき**。具体的には:

1. §7「正しさ vs 快適さ」フレームを廃止し、「人間-AI 協働における framework の
   読みやすさ / 生成しやすさ / 変更しやすさ」軸で再構成
2. §8 の弱点リストから、A・B 該当項目を削除
3. §10 の採用判断を「人間チームのプロパティ」から「使う AI tooling との適合度」
   に書き換え
4. §11 結論を「LLM ネイティブな reference」frame に統一し、対句を捨てる
5. wishes-to-author / skill-proposals と整合する論拠だけを残す

ただし書き直しは別タスク。本書はあくまで **何が問題だったかを特定する** ところ
までで止める。

## H. 自己観察として

私は「率直な振り返り」として自己批判はできた (build-log.md の振り返り)。
しかし「frame そのものが古い」ことには気づかなかった。

**自己批判は内容のレベルで止まりやすい。frame レベルの誤りは、外から指摘
されないと気付かない。** 今回ユーザーから「OOP を学ぶコストが必要」型の批判が
ナンセンス、人間が教える時代ではない、二項対立に陥っていないか、という
3 軸を渡されて初めて、自分の評論の軸が古いことが見えた。

このセルフレビュー自体は、ユーザーの指摘がなければ書けなかった。これも
人間-AI 協働の構造の一例として残しておく。
